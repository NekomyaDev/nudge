## 1. Capability and Why It Blocks Local Interactive Use

### Capability Overview
Pack 5 specifies a provider-agnostic Account, Credential, and Authorization subsystem for the Nudge language and native runtime. It transitions Nudge away from ambient environment variables and third-party host token harvesting into first-class language and runtime constructs: explicit account declarations, compile-time and runtime scope validation, fail-closed access gates, and standardized RFC 8628 (OAuth 2.0 Device Authorization Grant) interactive flows.

### Why Missing Provider Auth Blocks Local Interactive Use
1. **Interactive Session Failure**: When an engineer runs a `.ndg` script requiring an LLM model or an authenticated tool locally, Nudge assumes credentials already reside in the process environment (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`) or in a running local proxy. If credentials are missing, execution aborts ungracefully or silently falls back to dummy mock answers. The developer cannot authenticate interactively from the terminal.
2. **Parasitic File Insecurity**: The current implementation of `AntigravityProvider` covertly reads internal token files generated by other development tools (`~/.jcode/antigravity_oauth.json` and `~/.openhands/profiles/antigravity-proxy.json`). When executed on a pristine machine, in a container, in CI, or anywhere Jcode is not installed, the provider fails completely.
3. **Absence of Account and Scope Semantics**: Nudge programs have no syntax or runtime structure to express tenant accounts, permission boundaries, or credential lifetimes. All provider calls execute under ambient, unmanaged authority without verification of token scopes or expiration.

### Why "Reading a Ready Token File" Is Not a Solution
1. **Security and Trust Boundary Violation**: Opening `~/.jcode/` or `~/.openhands/` breaches process isolation. A programming language runtime must never snoop on private credentials written by distinct host applications without explicit user consent.
2. **Fragile and Unmanaged Lifecycles**: Foreign JSON token caches have unpredictable lifetimes. They expire, get revoked, or change format without Nudge having any contract to refresh them. When this occurs, Nudge crashes or fails silently.
3. **Environment Non-Reproducibility**: Programs requiring harvested host files cannot run in automated continuous integration pipelines, docker containers, or fresh developer workspaces.
4. **Architectural Parasitism**: Nudge must stand on its own foundations with clean, first-party authentication primitives.

## 3. Proposed Language and Runtime Design (Öneri)

### Language-Level Syntax: Account and Auth Declarations
Introduce first-class declarations in `.ndg` for authentication providers and accounts:

```nudge
// 1. Declare an authentication provider contract
auth provider anthropic {
    type: "api_key",
    env: "ANTHROPIC_API_KEY"
}

auth provider github_copilot {
    type: "device_code",
    issuer: "https://github.com/login/device/code",
    client_id: "Iv1.b507a08c87ecfe81",
    scope: "read:user model:inference"
}

// 2. Declare an account bound to a provider with explicit scopes
account dev_tier for github_copilot {
    scope: ["model:inference"]
}

// 3. Functions explicitly state their Auth requirement
fn query_engine(prompt: string) -> string
    uses LLM, Auth(dev_tier)
{
    prompt("Analyze: {prompt}")
}
```

### Runtime Architecture (`crates/nudge-runtime/src/auth/`)
Implement a dedicated authentication module inside `nudge-runtime`:
1. `Credential`:
   ```rust
   pub enum Credential {
       ApiKey(String),
       OAuthToken {
           access_token: String,
           refresh_token: Option<String>,
           expires_at: Option<u64>,
           scopes: Vec<String>,
       },
   }
   ```
2. `TokenStore`:
   - An isolated, secure credential store located strictly in Nudge's own configuration path: `~/.nudge/credentials.json`.
   - Files are created with restricted file permissions (`0600` on POSIX systems).
   - Under no circumstances does this store interact with other application paths.
3. `DeviceFlowClient`:
   - Fully native RFC 8628 (OAuth 2.0 Device Authorization Grant) client using in-process HTTP (`ureq` + `rustls`).
   - Handles device code generation, user code presentation, polling intervals with exponential backoff, and token persistence.
4. `AccountRegistry`:
   - Validates that the active account satisfies all scopes required by the requested action.

## 4. Type and Effect Semantics

### The `Auth` Effect
Authentication is treated as a typed effect in Nudge:
- Effect signature: `uses Auth(<account_name>)` or `uses Auth`.
- Calling a function that requires `Auth(acc)` requires either the enclosing function to declare `uses Auth(acc)` or execution inside a scoped `auth using <account>` block.
- Pure functions (`uses none`) are forbidden from invoking authenticated operations.

### Scope Verification
- Scopes are modeled as verified strings (e.g. `model:inference`, `tools:web_search`).
- Before any network packet is dispatched, the runtime verifies that the active credential holds the requested scope.
- Inability to satisfy the scope triggers a fail-closed halt with error code `E-auth-0403`.

### Error Diagnostic Codes
Conforming to Nudge compiler diagnostic standards:
- `error[E-auth-0401]`: Credential missing or uninitialized for the specified provider and account.
- `error[E-auth-0402]`: Device code flow expired, timed out, or was rejected by user.
- `error[E-auth-0403]`: Scope deficit. Account does not have the required permissions.
- `error[E-auth-0404]`: Provider adapter disabled. No proven official public OAuth contract exists.
- `error[E-auth-0405]`: Corrupted, insecure, or unreadable Nudge credential store.

## 5. Local Execution Behavior

### Non-Interactive Execution (CI, Batch Jobs, Daemons)
- If required credentials are not found in `~/.nudge/credentials.json` or explicitly set via `NUDGE_AUTH_*` environment variables, execution immediately fails closed with `error[E-auth-0401]`.
- Nudge never stalls waiting for input in non-interactive mode and never falls back silently to mock providers.

### Interactive Terminal Execution
- When standard input is an interactive TTY and a device-flow credential is missing or expired, Nudge initiates RFC 8628 authentication:
  ```text
  [nudge auth] Action requires authentication for account 'dev_tier'.
  [nudge auth] To complete login, visit: https://github.com/login/device
  [nudge auth] Enter code: 7C12-882E
  [nudge auth] Waiting for authorization...
  ```
- Polling runs until authorized or timed out. On success, the token is saved to `~/.nudge/credentials.json` and execution resumes automatically.

## 6. Security Boundary and Per-Provider Gate

### Universal Hard Security Boundaries
- **Zero Third-Party File Reading**: The runtime is strictly prohibited from accessing files belonging to other applications (including `~/.jcode/`, `~/.openhands/`, etc.). All code reading foreign directories must be permanently excised.
- **Fail-Closed Execution**: If credentials are missing, invalid, or expired, execution halts with a definitive error. Silent substitution of `FakeProvider` for missing credentials when a live provider was requested is eliminated.

### Provider Status Matrix (Official Public Verification Gate)
In accordance with Hard Rule (2), if a provider's official OAuth method cannot be proven from its public documentation, that adapter's OAuth capabilities stay DISABLED:

| Provider | Official Public OAuth / Device Flow Status | Adapter Policy |
| :--- | :--- | :--- |
| **`antigravity`** | **UNPROVEN / PROPRIETARY**. No public RFC 8628 device flow or developer OAuth endpoint exists in public documentation. Existing implementation relied on stolen Jcode tokens. | **DISABLED (OFF)**. The adapter and its file-harvesting code are removed. It remains disabled until an official public standard contract is proven. |
| **`openai`** | **UNPROVEN FOR OAUTH**. OpenAI public developer API only provides API key authentication (`OPENAI_API_KEY`). There is no public RFC 8628 Device Code or PKCE flow for 3rd-party developer CLI tools. | **OAUTH DISABLED**. Adapter operates exclusively via explicit user-provided API keys (`apiKey`). Pseudo-OAuth or scraping tokens is strictly forbidden. |
| **`claude`** | **UNPROVEN FOR OAUTH**. Anthropic API strictly requires `x-api-key`. No public RFC 8628 Device Authorization flow exists for third-party CLIs. | **OAUTH DISABLED**. Adapter operates exclusively via explicit user-provided API keys (`apiKey`). |
| **`github_copilot`** | **PROVEN (RFC 8628)**. GitHub officially documents and maintains RFC 8628 Device Authorization Grant endpoints (`https://github.com/login/device/code`). | **ENABLED FOR DEVICE FLOW**. Implements official RFC 8628 contract with explicit client configuration. |

## 8. VM-Path Note

### Confirmed Source Behaviors
- **VM Default Engine**: In `crates/nudgec/src/eval/interpreter.rs:1734-1736` (Commit `fc14ea1`), `run_program()` initializes and executes the NBC Bytecode VM unless explicitly disabled via `NUDGE_VM == "0"`.
- **Effect Rejection at Compile Time**: In `crates/nudgec/src/bytecode.rs:873-877` (Commit `a3b55a9`), bytecode compilation rejects entry functions that declare effects (e.g. `uses LLM`). In such cases, `run_program()` falls back directly to the AST interpreter (`crates/nudgec/src/eval/interpreter.rs:1758-1760`).
- **Effect Delegation**: For pure entry functions containing nested effectful expressions, the VM emits `Op::DelegateCall` (`crates/nudgec/src/vm.rs:574`) and `Op::DelegateExpr` (`crates/nudgec/src/vm.rs:593`), delegating execution back to the AST interpreter through `DelegateHook` (`crates/nudgec/src/eval/interpreter.rs:1739-1751`).
- **Runtime Provider Dispatch**: The Bytecode VM contains no network, socket, or credential logic. All provider and authentication operations route through the AST interpreter and runtime layers (`crates/nudge-runtime/src/provider/`, `crates/nudge-runtime/src/trace.rs:863`).

### Limitations Not Provable from Source
- The current bytecode instruction format has no instructions or operand slots for account capabilities or credentials. Whether future VM revisions will receive an ambient execution context pointer or resolve credentials during bytecode compilation cannot be determined from existing source code.
